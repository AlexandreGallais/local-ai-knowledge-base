# Architecture review checklist

Contents: A. Goals · B. Decomposition · C. .NET structure · D. API contract · E. Real-time · F. Messaging · G. .NET services · H. Data · I. Angular · J. Live display · K. Libraries · Sources
Answer each question with yes, no or unknown. A "no" is a finding. An "unknown" is a question for the user.

## A. Goals and decisions (always)

- Are the quality goals written and ranked?
- Is there a record of the main decisions, each with its reason and the rejected alternative?
- Does each deployable unit, layer and library have a stated reason?

## B. Decomposition (when there is more than one deployable unit, or a split is proposed)

- Does each service exist for a stated need: a team that releases alone, a load to scale alone, a failure to isolate?
- Are the boundaries drawn around business capabilities, not technical layers?
- Does each service or module own its data? No table is read by two of them.
- Can each service be released without releasing another one the same day?
- Is one business operation done without a long chain of calls between services?
- If the team is small and the services are released together: is a modular monolith ruled out for a stated reason?

## C. .NET solution structure (when there is .NET code)

- Is the code organized by feature or module, with a public interface per module?
- Does each layer do work? No service or repository only forwards calls.
- Is CQRS used only where reads and writes differ? Not on simple CRUD.
- Are commands and queries plain classes called directly, with no mediator library required?
- Is there a test that enforces the dependency rules between modules or layers?

## D. API contract (when Angular calls a .NET API)

- Is the OpenAPI document generated by the built-in ASP.NET Core package, at build time?
- Is the generated document committed, so that a contract change shows in a diff?
- Is the Angular client generated from that document, not written by hand?
- Does the client generator support every schema the API emits? Check the OpenAPI version, `oneOf` and `anyOf`.
- Is the API version explicit, and are breaking changes shipped as a new version?
- Do errors use the problem details format, and is request validation enabled?
- Is the OpenAPI endpoint closed or protected outside development?

## E. Real-time (when the server pushes data to the browser)

- Is the transport chosen for the need: SignalR for two-way or groups, server-sent events for a simple one-way stream? gRPC is not called from the browser.
- With more than one replica: is session affinity set, or do all clients use WebSockets only with negotiation skipped?
- With more than one replica: is there a backplane?
- Are clients subscribed only to the views they display, through groups?
- Are changes sent in batches at a fixed rate, not one message per value?
- Is each message under the receive size limit? Is MessagePack considered when size matters?
- Are detailed errors off in production?
- Was the message rate measured against the goal?

## F. Messaging (when a queue or a bus is used or proposed)

- Is there a stated need to decouple in time: long work, retry after failure, several subscribers?
- Is a message written in the same transaction as the data, through an outbox?
- Are consumers idempotent?
- Is the license of the messaging library checked for its exact version?

## G. .NET service patterns (when there is .NET code)

- Does no singleton hold a scoped service?
- Are options bound, validated and checked at start?
- Is there exactly one resilience handler per HTTP client, with retries off for unsafe methods?
- Do log messages use named placeholders?
- Are logs, metrics and traces exported with OpenTelemetry?
- Are readiness and liveness checks separate? The liveness check calls no dependency.

## H. Data access (when a database is used)

- Is each database context short-lived, one per unit of work?
- Is no context used by two operations at the same time?
- Do data tests run against the real database engine?

## I. Angular structure and state (when there is Angular code)

- Are folders organized by feature, not by type?
- Are components standalone, with lazy-loaded feature routes?
- Is local state in signals, and derived state in `computed`?
- Is shared state in a service with signals? A store library is used only for a stated need.
- Are server reads done with `httpResource` or a service, and writes with `HttpClient`?
- With several apps or libraries: is there a lint rule that enforces module boundaries?

## J. Angular live display (when the screen shows values that change often)

- Does each displayed value come from a signal?
- Is each symbol a small component, with as few DOM nodes as possible?
- Are lists rendered with `@for` and `track`?
- Are incoming messages grouped before they update signals?
- Is heavy computation moved off the main thread?
- Was the display measured before any further optimization?

## K. Libraries and licenses (always)

- Is each library checked in `outdated-libraries-and-patterns.md`?
- For a library with a paid or restricted license: is the version pinned and the decision recorded?
- Does the code use a pattern listed as outdated for its framework version?
